# E3.c4: cut posterior with random kernel densities

Mechanism. Draw M sets of Bayesian-bootstrap weights w⁽ᵐ⁾. Each set gives densities f̂⁽ʷ⁾ⱼ and a matrix C⁽ʷ⁾. Run NUTS on π with each f̂⁽ʷ⁾ⱼ, and pool the draws. By the law of total variance,

$$\operatorname{Var}(\pi)=\underbrace{\mathbb E_w\big[\operatorname{Var}(\pi\mid w)\big]}_{\approx\,e_1^U\text{ (current)}}+\underbrace{\operatorname{Var}_w\big(\mathbb E[\pi\mid w]\big)}_{e_1^V\text{ (new)}}.$$

## What it adds beyond E3.c3.

- The e₁^V term.
- Coherence. The same w moves the recalls of h and the densities of the quantifier together. If an easy V inflates both, their errors on accuracy are correlated; E3.c3 assumes they are independent. The marginal of C⁽ʷ⁾ is Dir(f) exactly as in E3.c3 (with the a=0 convention), so E3.c4 minus E3.c3 isolates e₁^V plus the coupling. That is a clean reason to run E3.c3 first.

### Why doesn't BayCAP-KDEy already take into account $e_1^V$?
Because BayesKDEy treats the class densities $\hat f_j$ as known and exact. They are computed once from $V$ and plugged into the likelihood as fixed numbers.

The posterior is conditional on $V$. BayesKDEy samples

$$p(\pi\mid U,\hat f)\propto p(\pi)\prod_{i=1}^{N^Q}\sum_j\pi_j,\hat f_j(z_i).$$

The only unknown in this model is $\pi$. There is no parameter that says "the densities might be wrong", so the posterior can only express uncertainty from having finitely many target outputs $z_1,\dots,z_{N^Q}$, which is $e_1^U$. As $N^Q$ grows, the posterior shrinks around the $\pi$ that best fits the bag under these particular $\hat f_j$, even if they are off.

$e_1^V$ is variation across validation sets. A different draw of $V$ would give different densities $\hat f_j$, so a different posterior with a different centre. By the law of total variance over both sources of randomness:

$$\operatorname{Var}(\pi)=\underbrace{\mathbb E_V\big[\operatorname{Var}(\pi\mid U,V)\big]}_{e_1^U:\ \text{what BayesKDEy reports}}+\underbrace{\operatorname{Var}V\big(\mathbb E[\pi\mid U,V]\big)}{e_1^V:\ \text{how the centre moves with }V}.$$

BayesKDEy sees one $V$, so it can only report the first term. The second term shows up as a shift of the centre, not as extra width. This is why, in §T.9, missing terms move the interval without widening it.

Contrast with BayesianCC. There, the analogue of the densities is the rate matrix $C$, and BayesianCC treats $C$ as unknown: it has a prior on $C$ and a likelihood from the validation counts. So its posterior on $\pi$ already includes the uncertainty from $V$. BayesKDEy has no equivalent parameters for the densities. E3.c4 adds them indirectly, through the bootstrap weights, and E3.c5 would add them as real parameters.

A bias part is missing too. Part of $e_1^V$ is systematic, for example a bandwidth $b$ that over-smooths or under-smooths. That is not represented either, and E3.c4 would not fix it, since re-weighting adds spread, not corrections.

## Limits.

- Bias. The bootstrap gives variance, not bias. It does nothing for a wrong bandwidth, for wine-quality, or for a systematic difference between V and the test pool.
- Very small classes. With 3 instances, the bootstrap can only reweight 3 fixed bumps. It cannot place mass where no validation point is, so it understates e₁^V exactly on poker_hand, the case that motivates it. I'd expect it to help there only partly.
- Evaluation. e₁^V is also fixed per V, so the standardised-shift evaluation and the toy argument of E3.c3 apply here too.

## Cost is the real problem: M NUTS runs per bag. Three ways to cut it [new hypotheses]:

1. Kernel matrix once. Compute the N^Q×| V| kernel matrix K_b(zᵢ,zᵥ) once per bag. Each f̂⁽ʷ⁾ⱼ(zᵢ) is then a matrix-vector product, so the cost of the densities is negligible.
2. Fewer draws per weight set. Keep the 500 warm-up steps but take R/M draws per run. With M=20 that is 20×(500+50)=11,000 steps against 1,500, about 7× the current cost. Warm-starting each run from the previous one could shorten the warm-up.
3. Laplace approximation instead of NUTS. For each w, find the posterior mode and its curvature in the ILR coordinates, then pool the M Gaussians. With N^Q=1000 the posterior given w is close to Gaussian, so this should be accurate and costs only M optimisations. Reusing one NUTS run by importance reweighting would be cheaper still, but the likelihood ratios over 1000 points would be too extreme to be usable.

# Question 1

> can you explain in simpler terms the theory behind c4? what do you mean when you talk about wheights? does it have to do with how KDE works?

## The short answer

Yes, it comes straight from how KDE works. A KDE gives each validation point a weight. Normally every point of a class gets the same weight. E3.c4 makes those weights random, to mimic "what if we had drawn a different validation set".

## Step 1: KDE already uses weights

BayesKDEy needs, for each class $\omega_j$, the density $f_j(z)$ of the classifier outputs within that class. It estimates it from the $n^s_j$ validation instances of that class (§T.3). It places one bump $K_b(z,z_v)$ on each validation output and averages them:

$$\hat f_j(z)=\sum_{v\in V_j}\frac{1}{n^s_j}\,K_b(z,z_v).$$

Every point has the weight $1/n^s_j$, and the weights sum to one, so $\hat f_j$ is a proper density. If one point had weight $0.5$ and the others less, its bump would count more and the density would lean towards it. In general, with weights $w_{j,v}\ge0$ that sum to one:

$$\hat f^{(w)}_j(z)=\sum_{v\in V_j}w_{j,v}\,K_b(z,z_v).$$

The standard KDE is the special case where all weights are equal.

### what is $z$ and $K_b(z,z_v)$?

$z$ is an output vector of the input classifier. For an instance $x$, $z=s(x)$ is the vector of class probabilities that the input classifier $s$ returns: $h$ itself (level h) or the MLP trained on $V$ (level mlp). With $K$ classes, $z=(z_1,\dots,z_K)$, with $z_k\ge0$ and $\sum_kz_k=1$, so it is a point on the simplex.

- $z_v$ is the output for one validation instance $v$. It is fixed, because it was computed once on $V$ (cross-fitted for the MLP).
- $z$ with no subscript is the point where we evaluate the density, typically the output $z_i$ of a target instance of the bag $U$.

In the binary example of the last answer I wrote only the score of class $\omega_1$. The full output there is $z=(z_1,1-z_1)$, so one number is enough to describe it.

$K_b(z,z_v)$ is the kernel, the "bump" centred on the validation output $z_v$. In E3.1 it is a Gaussian:

$$K_b(z,z_v)=c_b\exp!\left(-\frac{\lVert z-z_v\rVert^2}{2b^2}\right).$$

- $\lVert z-z_v\rVert$ is the ordinary (Euclidean) distance between the two output vectors.
- $b$ is the bandwidth, the width of the bump: $b=0.1$ in E3.1.
- $c_b$ is a constant that makes the bump integrate to one, so that it is a density.

How to read it: $K_b(z,z_v)$ is large when $z$ is close to $z_v$ and falls quickly once $z$ is more than a few multiples of $b$ away. It measures how much the validation point $z_v$ "vouches for" an output near $z$.

How it is used: the density of class $\omega_j$ at $z$ is the weighted sum of the bumps of that class's validation points:

$$\hat f_j(z)=\sum_{v\in V_j}w_{j,v},K_b(z,z_v).$$

With equal weights $w_{j,v}=1/n^s_j$ this is the standard KDE. With random weights it is the Bayesian-bootstrap version of E3.c4.

Why it matters for the quantifier: for each target output $z_i$, BayesKDEy compares the class densities $\hat f_1(z_i),\dots,\hat f_K(z_i)$. A target output that falls among many validation outputs of class $\omega_j$ gets a large $\hat f_j(z_i)$. That is evidence that class $\omega_j$ is frequent in the bag.

A note on notation: the $K$ in $K_b$ (the kernel) is unrelated to $K$, the number of classes. The clash comes from the standard notation in the KDE literature. In a document it might be worth renaming the kernel, for example $\kappa_b$.

### how does kde use f(z) and how is it instead used in a quantifier like KDEy?

Strictly speaking, KDE doesn't use $f(z)$: it estimates it. KDEy is the step that turns those estimated densities into an estimate of the prevalences.

#### 1. KDE by itself: a density estimator

KDE answers one question: given some points, how are they spread? It takes the points $z_v$ and returns a function $\hat f(z)$ that can be evaluated anywhere:

$$\hat f(z)=\frac1n\sum_{v}K_b(z,z_v).$$

That is all KDE does. It knows nothing about classes or prevalences. You give it points and get back a smooth histogram.

#### 2. KDEy: KDE as a building block of a quantifier

KDEy applies KDE several times and then adds a model on top.

**Step A: one density per class, from $V$.** For each class $\omega_j$, run a KDE on the outputs of its validation instances only. This gives $\hat f_1(z),\dots,\hat f_K(z)$, where $\hat f_j$ answers: "if an instance is of class $\omega_j$, where does its output $z$ tend to fall?" This step uses the labels of $V$.

**Step B: the mixture model.** Under prior probability shift, the densities $f_j$ are the same in $V$ and in the target; only the class proportions change. A target instance is drawn by first picking a class $\omega_j$ with probability $\pi_j$, then an output from $f_j$. By the law of total probability, the density of target outputs is

$$g_\pi(z)=\sum_j\pi_j,\hat f_j(z).$$

Each choice of $\pi$ gives a different mix of the class densities.

**Step C: choose $\pi$ so the mixture fits the target outputs.** We observe the outputs $z_1,\dots,z_{N^Q}$ of the bag $U$, without labels. KDEy looks for the $\pi$ under which these observed outputs are most plausible. In its maximum-likelihood version, the point estimate is

$$\hat\pi=\arg\max_\pi\sum_{i=1}^{N^Q}\log\sum_j\pi_j,\hat f_j(z_i).$$

KDEy also has variants that instead minimise a distance, such as Hellinger or Cauchy–Schwarz, between $g_\pi$ and a KDE of the target outputs. The idea is the same.

**Small example (binary).** Suppose a target output $z_i$ falls where $\hat f_1(z_i)=3$ and $\hat f_2(z_i)=0.5$. This instance "votes" mostly for class $\omega_1$. If most target outputs vote like that, the likelihood is largest at a high $\pi_1$. Unlike counting arg-max predictions, these votes are soft: an output where the two densities overlap supports both classes, in proportion to the densities.

#### 3. BayesKDEy: the same model, with a posterior instead of a point

BayesKDEy keeps steps A and B unchanged. In step C, instead of taking only the best $\pi$, it combines the same likelihood with a prior $\operatorname{Dir}(\mathbf 1)$ and samples the posterior with NUTS:

$$p(\pi\mid U)\propto p(\pi)\prod_{i=1}^{N^Q}\sum_j\pi_j,\hat f_j(z_i).$$

The draws $\pi^{(r)}$ are what BayCAP-KDEy then pushes through $\hat C$.

Where the weights of E3.c4 enter

Only in step A. Re-weighting the validation points changes each $\hat f_j$. That changes the values $\hat f_j(z_i)$ in the likelihood of step C, and so the posterior of $\pi$. Steps B and C are untouched.


## Step 2: the problem is that $V$ is one random sample

The validation set is one draw from the population. Another draw of $V$ would contain other points: an easier sample, a harder one, a different spread of outputs. That would give a different $\hat f_j$, and so a different posterior on $\pi$. BayesKDEy treats $\hat f_j$ as exact. Its posterior reflects only how few target instances we see (the spread from the target bag, called $e_1^U$), not how few validation instances we had (the spread from $V$, called $e_1^V$). That missing spread is what E3.c4 adds.

We cannot draw new validation sets, so we imitate them by re-weighting the points we have.

### Is this done in a similar fashion to what is done by BayesCC with matrix C?

Yes, the idea is the same. There are three differences: the kind of data, the prior, and whether the target bag also updates the uncertainty.

**What BayesianCC does with $C$.** The validation data enter only through the counts $f_{ij}$: how many instances of class $\omega_j$ the classifier $h$ predicts as $\omega_i$. The model says the column of counts is multinomial, $f_{\cdot j}\sim\operatorname{Mult}(n^s_j,C_{\cdot j})$, and the prior on the column is $\operatorname{Dir}(\mathbf 1)$. A Dirichlet prior combined with multinomial counts gives a Dirichlet posterior whose parameters are the prior parameters plus the counts. So, from $V$ alone,

  $$C_{\cdot j}\mid V\sim\operatorname{Dir}(\mathbf 1+f_{\cdot j}).$$

  Each draw of $C$ is a plausible alternative rate matrix: the same idea of "what $V$ could have looked like".

  **What the Bayesian bootstrap does.** BayesKDEy does not reduce $V$ to $K$ counts. It uses the continuous outputs $z_v$, and two different outputs are never the same category. So the Bayesian bootstrap treats each observed validation point as its own category and puts a Dirichlet on them, $w_j\sim\operatorname{Dir}(1,\dots,1)$, one coordinate per point of $V_j$. Formally, this is the posterior of a Dirichlet process (a Dirichlet over infinitely many categories) when the prior weight goes to zero: only the observed points keep any mass.

  **The link.** If you group the bootstrap weights by the prediction of $h$, the aggregation property gives

  $$C^{(w)}{\cdot j}\sim\operatorname{Dir}(f{\cdot j}).$$

  This is BayesianCC's posterior from $V$ alone, with prior $\operatorname{Dir}(\mathbf 0)$ in place of $\operatorname{Dir}(\mathbf 1)$. On $C$, the two approaches coincide up to the prior. The bootstrap version extends the same idea from counts to continuous outputs, so it can randomise the densities $\hat f_j$ as well.

  **The differences:**

  1. Prior. BayesianCC's $\operatorname{Dir}(\mathbf{1})$ adds one pseudo-instance per cell. It pulls the recalls towards $1/K$, but it also keeps cells with $f_{ij}=0$ uncertain. The bootstrap has no prior: no pull, but zero cells stay at zero, and the density can never put mass away from the observed points.
  2. Updating by the target bag. BayesianCC samples $(\pi,C)$ jointly, so the predictions of $h$ on $U$ also update $C$. E3.c4 is a cut posterior: the weights come from $V$ only, and $U$ updates only $\pi$. The real analogue of BayesianCC is E3.c5, where $U$ also updates the weights.
  3. Size. BayesianCC randomises $K(K-1)$ free numbers. The bootstrap randomises one weight per validation point, $\lvert V\rvert$ in total. That doesn't matter for E3.c4, where the weights are drawn directly, but it makes E3.c5 expensive.

## Step 3: the bootstrap is re-weighting

The ordinary bootstrap resamples $V_j$ with replacement: $n^s_j$ picks, each a uniformly random point. A point picked twice counts double; a point never picked drops out. That is the same as giving each point the weight (number of times it was picked)$/n^s_j$.

**Example** (binary, $z$ = score of class $\omega_1$; $h$ predicts $\omega_1$ when $z>0.5$). Class $\omega_1$ has four validation outputs:

| point | $z_v$ | standard weight | one bootstrap resample | one Bayesian-bootstrap draw |
| ----- | ----- | --------------- | ---------------------- | --------------------------- |
| 1     | 0.9   | 0.25            | 0.50 (picked twice)    | 0.10                        |
| 2     | 0.8   | 0.25            | 0 (not picked)         | 0.15                        |
| 3     | 0.7   | 0.25            | 0.25                   | 0.20                        |
| 4     | 0.3   | 0.25            | 0.25                   | 0.55                        |

In the last column, point 4 (a misclassified instance) counts a lot. The density of class $\omega_1$ shifts towards low scores, as if this validation sample had been "harder".

The **Bayesian bootstrap** (Rubin, 1981) replaces the integer counts with smooth random weights, drawn from $\operatorname{Dir}(1,\dots,1)$: non-negative, summing to one, and uniform over all such vectors. It behaves almost like the ordinary bootstrap. With $n=n^s_j$:

- **Mean:** each weight has mean $1/n$ under both.
- **Ordinary bootstrap variance:** the count of a point is $\operatorname{Bin}(n,1/n)$, with variance $1-1/n$, so its weight has variance $(1-1/n)/n^2=(n-1)/n^3$.
- **Dirichlet variance:** $\operatorname{Var}(w_v)=\frac{(n-1)}{n^2(n+1)}$.
- **Ratio:** the two variances differ by the factor $n/(n+1)\approx1$.

The Dirichlet version is chosen because it is smooth (no points dropped exactly) and has a Bayesian reading: it is a posterior over "the true distribution of class $\omega_j$", supported on the observed points.

## Step 4: one weight draw gives a density and a rate matrix

The same weights also give a rate matrix for $h$. The recall of class $\omega_1$ is the weighted share of its points that $h$ predicts correctly:

$$C^{(w)}_{ij}=\sum_{v\in V_j}w_{j,v}\,\mathbf 1[h(v)=\omega_i].$$

In the example, points 1–3 are predicted correctly. The standard recall is $0.75$, and in the Bayesian-bootstrap draw it is $0.10+0.15+0.20=0.45$. The same "harder" validation sample moves the density of the quantifier and lowers the recall of $h$ at the same time. That is what I meant by "coherent": both come from one imagined alternative $V$. E3.c3 instead draws $C$ alone, independently of $\pi$.

The recall's distribution comes from the aggregation property (Appendix B): grouping the weights by the prediction of $h$ gives $C^{(w)}_{\cdot j}\sim\operatorname{Dir}(f_{1j},\dots,f_{Kj})$. So the $C$ part of E3.c4 is exactly E3.c3.

## Step 5: the procedure

For $m=1,\dots,M$:

1. draw weights $w^{(m)}$ for every class;
2. build $\hat f^{(w^{(m)})}_j$ and $C^{(w^{(m)})}$;
3. run BayesKDEy on the target bag with these densities, giving draws of $\pi$;
4. push those draws through $C^{(w^{(m)})}$ with the realised pushforward.

Finally, pool all the samples of $M$ runs into one interval.

The pooled spread has two parts, by the law of total variance. One is the spread within a run: the target bag is finite, which is what we have today. The other is the spread between runs: the validation set is finite, which is the new part.

**Why "cut".** The weights come from $V$ alone; the target bag never updates them. A full Bayesian model would let $U$ also inform the weights. That is E3.c5, with $\lvert V\rvert$ extra parameters. "Cut" means we deliberately cut that feedback, to keep the model simple and cheap.

### Isn't this approach slow compared to other bayesian CAP approaches, given it needs $M$ re-runs?

Yes. Run naively, E3.c4 costs about $M$ times one BayCAP-KDEy method, while the other Bayesian CAP methods need a single NUTS run per bag:

- BayesCAP: one NUTS run on $(\pi,C)$, with $K-1+K(K-1)$ free parameters.
- BayCAP-KDEy (E3.1): one NUTS run on $\pi$, with $K-1$ parameters.
- E3.c3: the same single run. Drawing $C$ from a Dirichlet costs almost nothing.
- E3.c4, naive: $M$ NUTS runs per bag, each with its own 500 warm-up steps.

E3.1 recorded no timings (time measurements were set aside as optional), so I can only reason in multiples of one run, not in seconds.

The $M\times$ factor can be reduced a lot [new hypotheses, untested]:

1. **Densities are cheap to recompute.** Compute the kernel matrix $K_b(z_i,z_v)$ between target and validation outputs once per bag. Each weight draw then needs one matrix-vector product to get $\hat f^{(w)}_j(z_i)$. The cost of E3.c4 is the sampling, not the KDE.
2. **Split the draws.** Instead of $M$ full runs of 1000 draws, take $1000/M$ draws per weight set. Only the warm-up is repeated: with $M=20$, about $20\times(500+50)=11{,}000$ steps against $1{,}500$, about $7\times$, not $20\times$. Warm-starting each run from the previous weight set's posterior could shorten the warm-up further.
3. **Vectorise.** The $M$ runs have the same model shape and differ only in the precomputed density values. They could be run as $M$ parallel chains in one vectorised call. The total work stays the same, but the wall-clock time drops if the hardware allows it.
4. **Replace NUTS with a Laplace approximation.** With $N^Q=1000$, the posterior of $\pi$ given one weight set is close to Gaussian. Find its mode and curvature by optimisation, draw from that Gaussian, and pool the $M$ results. $M$ small optimisations may cost less than one NUTS run, so E3.c4 could end up cheaper than E3.1. The price is an approximation that must be checked against NUTS on a few bags.

E3.c4 is also not much heavier per step than BayesCAP: its log-likelihood uses precomputed values ($N^Q\times K$ numbers), and $\pi$ has only $K-1$ parameters, against BayesCAP's $K^2-1$.

## What it cannot do

Every imagined validation set is made of the same points, only re-weighted. With 3 validation instances in a class (`poker_hand`), the alternatives are just different mixes of 3 bumps at fixed places. A truly new validation set could put points elsewhere, so the method understates the uncertainty exactly where $V$ is smallest. It also adds only spread, never a correction: if the KDE is biased, for example by a poor bandwidth $b$, or if $V$ systematically differs from the test pool, the interval gets wider but stays off-centre.
